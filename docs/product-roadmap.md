# Training Planner product roadmap

## Scope and sequencing

This is a proposed, evidence-grounded backlog, not a claim of user demand, scientific validation, or market superiority. Order is a recommendation based on the verified baseline, dependencies, and proposed risk controls; review candidate sequencing before implementation.

**Current milestone (M0) — documentation only:** create this roadmap. No application behavior changes are part of this delivery. M0 is separate from every feature candidate below.

**First later feature candidate — TP-01:** let an owner edit a saved training note. It is the Phase 1, P0 candidate, not part of M0 or the current documentation milestone. The UX reviewer also recommended a clear empty-dashboard-to-setup path (TP-04); retain it as a later candidate, not a user-research finding or a replacement for TP-01's first-candidate framing.

### Scales and estimation caveat

- **Priority:** P0 = first candidate for the next feature milestone; P1 = core journey, day-planning, and foundational high-impact privacy work; P2 = training, coaching, integration, and other privacy capabilities; P3 = accessibility, reliability, and growth work. Priority is proposed sequencing, not measured demand.
- **User-impact hypothesis:** H = likely to affect a core task or sensitive access boundary; M = likely to improve a common workflow or understanding; L = narrower or incremental benefit. These are hypotheses, not user research.
- **Safety/privacy review:** `required` means obtain an appropriate Safety & Privacy Reviewer review before implementation begins, and revisit it before release if scope or data flows change; it is a prerequisite, not approval, authorization to launch, or a substitute for product decisions, validation, or applicable obligations. Any item that introduces personal/sensitive data, identity, sharing, an external provider, AI, or account-lifecycle handling must be treated as `required`, even if its scope changes from the estimate here. `standard` means normal project review and tests still apply only while that scope remains non-sensitive.
- **Effort:** S = bounded change; M = multiple UI/service/test changes; L = broader integration, architecture, or operational work. All effort estimates are hypotheses, not estimates validated through delivery.
- Acceptance outcomes below are proposed, testable completion checks. They do not assert that the behavior currently exists.

## Baseline and evidence basis

The following paths and tests ground the backlog; the evidence is limited to the reviewed files and supplied Product Owner inspection:

- `app.py` gathers an athlete profile and then routes through the app. Goal event date/distance are configured later in `pages/settings.py`. `pages/dashboard.py` directs a user without a plan to Settings; `pages/training_plan.py` supports run and planned-strength logging.
- `pages/notes.py` and `pages/events.py` add and delete records but do not offer editing. `services/plan_service.py` contains plan synchronization and scoped plan operations.
- `pages/ai_coach.py` and `services/ai_service.py` apply validated AI changes on review; applied changes are reversible. Safety bounds and missed-session behavior are documented in `README.md`.
- Garmin recovery context is consent-gated in `pages/profile.py` and `services/ai_service.py`. Hosted account integration exists in `pages/settings.py` and `services/garmin_accounts.py`, while `pages/garmin.py` says hosted linking is unavailable, conflicting with the Settings path and `README.md`.
- `pages/friends.py` and `services/plan_service.py` support accepted-friend access and limited future-plan edits. Account isolation, friendship authorization, and backup/restore behavior have test coverage.
- Relevant test evidence includes `tests/test_planner.py::test_missed_long_run_not_made_up` (line 22), `::test_missed_quality_not_moved_or_added` (line 32), `::test_backup_restore` (line 97), and `::test_authenticated_accounts_are_isolated` (line 122); `tests/test_new_features.py::test_accepted_friends_can_edit_future_runs_only`, `::test_ai_proposal_caps_and_taper_rules`, `::test_ai_changes_apply_and_can_be_reverted`, `::test_athlete_profile_setup_synchronizes_settings_and_builds_open_ended_plan`, `::test_garmin_wellness_context_requires_profile_consent`, and `::test_garmin_credentials_are_encrypted_and_account_scoped`; authentication coverage also includes `tests/test_auth.py`.
- In the reviewed test files and sections, no Streamlit end-to-end tests were observed. This observation is limited to files reviewed and is not an exhaustive repository-wide test inventory.

Product Designer's advice informs later candidates: reduce the empty-dashboard-to-setup dead end; make planned and logged sessions clear; preserve optional fields and consent; support mobile, keyboard, focus, and readable errors; and avoid suggesting that AI or Garmin data is diagnostic. These are design recommendations, not validated user needs.

## Assumptions and follow-up

- The listed backlog reflects the Product Owner's verified baseline and recommendations supplied for this artifact. Estimates, impact levels, sequencing, and acceptance checks are proposals; validate them during feature discovery and implementation planning.
- Preserve account isolation, existing logged user data, optional profile fields, and explicit recovery-data consent. Recheck server-side authorization and safety bounds for any implementation affecting shared data, AI, or external integrations.
- The first later feature candidate is TP-01; higher priority does not imply a commitment or user-demand finding. TP-04 retains the UX reviewer's recommendation to improve the empty-dashboard-to-setup path. TP-21 also requires a product decision about the default AI proposal interaction before implementation.
- This M0 delivery is the roadmap document only. It does not implement backlog items or independently verify all repository tests; a required privacy review is a prerequisite to sensitive-item implementation, not approval.
